
# Customer Representative Agent — MVP Build Specification

## 1. Objective

Build an MVP of a **Customer Representative AI Agent** using **LangGraph**.

The agent will act as the company's conversational customer representative. It must be able to understand a customer's messages, retrieve and reason over that customer's business data from MongoDB, answer questions accurately, create/update cases, initiate approval requests, and communicate management decisions.

The architecture MUST be designed so that the Customer Representative can later orchestrate other specialized agents such as Finance Agent, Sales Agent, Collections Agent, Support Agent, Credit Agent, etc.

For the MVP, however, implement the **Customer Representative Agent only** and create the abstractions/interfaces required for future multi-agent orchestration.

---

# 2. Core Product Behavior

The agent receives messages from a customer through a session-based interface such as WebSocket.

Example:

Customer:

> I made a payment last week. Why is my account still showing outstanding?

The agent should:

1. Identify the customer.
2. Load relevant customer context.
3. Retrieve relevant sales/invoices.
4. Retrieve receipts.
5. Understand whether receipts are:

   * against a specific reference/invoice, or
   * on account.
6. Retrieve relevant ledger entries.
7. Retrieve relevant vouchers/adjustments.
8. Determine the current outstanding position.
9. Explain the result in customer-friendly language.
10. Never invent accounting information.

The agent must also maintain conversational context within the session.

Example:

Customer:

> Why is invoice 1234 outstanding?

Agent:

> Invoice 1234 has an outstanding balance of ₹50,000.

Customer:

> But I paid 20,000 last week.

The agent should understand that "I paid 20,000 last week" is referring to the same customer/account/invoice context and investigate the relevant receipt.

# 3. MVP Scope

Implement these capabilities:

### Customer understanding

* Identify customer from authenticated/session context.
* Load customer profile.
* Load relevant customer financial context.
* Maintain conversation context.
* Resolve references such as:

  * "that invoice"
  * "that payment"
  * "my last payment"
  * "the previous complaint"
  * "that case"

### Financial understanding

Read and reason over:

* Customers
* Sales/invoices
* Receipts
* Ledgers
* Vouchers
* Outstanding balances

Important:

Receipts can be:

1. Against-reference receipts
2. On-account receipts

Do NOT assume an on-account receipt belongs to a particular invoice unless the database relationships/business rules establish that relationship.

The agent should preserve the distinction between:

```text
Invoice
Receipt against Invoice
Receipt on Account
Ledger Entry
Voucher / Adjustment
Outstanding
```

### Case management

The agent must be able to:

* Search existing cases.
* Retrieve a specific case.
* Create a new case.
* Update an existing case.
* Identify whether the customer's issue already has an open case.
* Avoid creating duplicate cases where an existing case covers the same issue.
* Communicate case status.

### Disputes

The agent should be able to recognize requests such as:

> I want to dispute this invoice.

and create a dispute case using a controlled tool.

### Approval requests

The agent should recognize requests such as:

> Please waive the late payment charge.

If the request requires management approval, create an approval request rather than pretending that the request was approved.

### Management decisions

The agent must be able to retrieve the current decision on an existing case/approval and communicate the decision to the customer.

For example:

```text
Pending
    ↓
Management Review
    ↓
Approved / Rejected
    ↓
Customer Representative
    ↓
Customer
```

### Payment reminders

Implement the data/service abstraction required to calculate:

* Current outstanding
* Previous payment dates
* Payment intervals
* Historical payment behavior

The MVP may expose payment-reminder analysis through a tool/service.

Do NOT allow the LLM to independently invent payment schedules.

# 4. Architecture

Use this architecture:

```text
Customer
   |
   v
Channel / WebSocket
   |
   v
Session Layer
   |
   v
Customer Representative Agent
          |
          +----------------------+
          |                      |
          v                      v
     Business Tools        Agent Gateway
          |                      |
          v                      v
       MongoDB              Future Agents
```

The Customer Representative is implemented as a **LangGraph stateful graph**.

Do not implement a monolithic "one giant agent prompt".

Use separate nodes/functions for:

* Session initialization
* Customer identification
* Context retrieval
* Intent understanding
* Agent reasoning/planning
* Tool execution
* Case workflows
* Approval workflows
* Response generation
* Persistence/finalization

# 5. LangGraph State

Create a typed state object.

Prefer Python `TypedDict` or an equivalent strongly typed state model.

Minimum state:

```python
class CustomerRepState:
    session_id: str
    customer_id: str | None

    messages: list
    conversation_summary: str | None

    current_intent: str | None
    extracted_entities: dict

    customer_context: dict
    financial_context: dict
    case_context: dict

    active_case_id: str | None

    pending_action: dict | None
    approval_required: bool

    tool_results: list
    agent_results: list

    response_context: dict

    errors: list
```

Keep the state extensible.

Do not hard-code the state in a way that prevents future agent delegation.

Add fields for:

```text
task_id
parent_task_id
requesting_agent
delegated_agent
```

even if they are not heavily used in the MVP.

# 9. MongoDB Access

MongoDB is the **source of truth**.

Do NOT give the LLM unrestricted MongoDB access.

Do NOT allow the LLM to generate arbitrary MongoDB queries and execute them directly in production.

Create a controlled repository/service layer.

Example:

```text
CustomerRepository
SalesRepository
ReceiptRepository
LedgerRepository
VoucherRepository
CaseRepository
ApprovalRepository
DecisionRepository
```

Then expose controlled business tools above those repositories.

Example:

```python
get_customer(customer_id)

get_customer_sales(
    customer_id,
    filters=None
)

get_customer_receipts(
    customer_id,
    filters=None
)

get_customer_ledger(
    customer_id,
    filters=None
)

get_customer_vouchers(
    customer_id,
    filters=None
)

get_customer_outstanding(
    customer_id
)

get_customer_cases(
    customer_id,
    status=None
)

get_case(case_id)

create_case(...)

update_case(...)

create_approval_request(...)

get_approval_status(...)

get_management_decision(...)
```

The repository layer owns MongoDB queries.

The tool layer owns business semantics.

The LLM only sees the tool interface.

# 10. Financial Context Builder

Create a dedicated service:

```text
FinancialContextService
```

Its job is to assemble a coherent financial picture for the customer.

Example output:

```json
{
  "customer_id": "...",
  "outstanding_balance": 72500,
  "sales": [],
  "receipts": [],
  "on_account_receipts": [],
  "ledger_entries": [],
  "vouchers": [],
  "reconciliation": {}
}
```

The exact schema should adapt to the existing MongoDB schema.

Do not invent fields if the actual database schema differs.

The context builder should support targeted retrieval.

Do not retrieve the customer's entire historical database for every message.

For example:

```text
Question about invoice
    ↓
Retrieve invoice
    ↓
Retrieve related receipts
    ↓
Retrieve relevant ledger entries
    ↓
Retrieve relevant vouchers
```

instead of loading thousands of unrelated records.

# 11. Receipt Interpretation

This is a critical accounting requirement.

The system must distinguish:

```text
Receipt A
  type = AGAINST_REFERENCE
  reference = INV-123
```

from:

```text
Receipt B
  type = ON_ACCOUNT
  reference = null
```

The agent must never say:

> "Your ₹20,000 on-account receipt paid invoice INV-123"

unless the accounting data/business rules establish that allocation.

When explaining balances, show the relationship explicitly.

Example:

```text
Invoice: ₹100,000
Receipt directly against invoice: ₹40,000
On-account receipt: ₹20,000
Other adjustment: ₹5,000
Calculated/reported outstanding: ₹55,000
```

If the accounting system's ledger gives a different authoritative balance, explain the ledger result rather than inventing a reconciliation.

# 14. Tool Execution Rules

Every write operation must be performed through a tool.

Examples:

```text
CREATE CASE
UPDATE CASE
CREATE APPROVAL
UPDATE APPROVAL
SEND CUSTOMER NOTIFICATION
```

Never allow the LLM to simulate tool execution.

The system should receive an actual tool result such as:

```json
{
  "success": true,
  "case_id": "CASE-12345"
}
```

before telling the customer:

> Your case CASE-12345 has been created.

# 15. Agent Gateway

Create an abstraction even though the MVP has only one agent.

Example:

```python
class AgentGateway:

    def discover_agents(self, capability: str):
        ...

    def delegate_task(
        self,
        agent_id: str,
        task: dict,
        context: dict
    ):
        ...

    def get_task_result(self, task_id: str):
        ...
```

Create an agent contract:

```python
class AgentTask:
    task_id: str
    parent_task_id: str | None
    requesting_agent: str
    target_agent: str
    customer_id: str
    intent: str
    context: dict
```

And:

```python
class AgentResult:
    task_id: str
    agent_id: str
    status: str

    findings: dict
    actions_taken: list
    pending_actions: list

    requires_human_approval: bool
    customer_communication_required: bool

    recommended_next_action: str | None
```

For MVP:

```text
AgentGateway
     |
     └── No external agents registered yet
```

But the Customer Rep graph should already route through the gateway abstraction when delegation is required.

# 16. Conversation / WebSocket Session

Create a session abstraction.

Minimum:

```python
session_id
customer_id
created_at
last_activity_at
conversation_history
current_context
active_case_id
```

The WebSocket layer should:

1. Receive message.
2. Associate it with session.
3. Associate session with customer.
4. Invoke LangGraph.
5. Stream/return response.
6. Persist interaction.

The LangGraph graph must be capable of continuing from previous state.

Do not create an entirely new unrelated context for every message.

# 17. Memory Strategy

Implement three levels of context:

### Short-term conversation memory

Current session messages.

```text
"that invoice"
"my previous payment"
"the case we discussed"
```

### Customer business context

Retrieved from MongoDB.

```text
Customer
Sales
Receipts
Ledger
Cases
Approvals
Decisions
```

### Persistent conversation history

Persist relevant conversations/interactions so future sessions can optionally use historical context.

Do not automatically stuff the entire historical conversation into every prompt.

Create a summarization/context mechanism.

# 18. Response Generation

The final response should be generated only after relevant tools/data have been retrieved.

Response principles:

* Be concise.
* Be customer-friendly.
* Be factually grounded.
* Distinguish confirmed facts from uncertainty.
* Never invent accounting data.
* Never invent case status.
* Never invent management decisions.
* Never claim an action succeeded without a successful tool result.
* Never expose internal reasoning.
* Never expose internal MongoDB implementation details.

Example:

```text
I checked your account and found a receipt of ₹40,000 dated 6 August.
That receipt is recorded against invoice INV-1234.

There is also a separate ₹20,000 receipt recorded on account.
I cannot treat that second receipt as payment against INV-1234 unless it has been allocated to the invoice.

Your current ledger balance shows ₹60,000 outstanding.
```

# 19. Security

Implement customer-level authorization.

A customer must never be able to retrieve another customer's:

* invoices
* receipts
* ledger
* cases
* approvals
* management decisions

The `customer_id` should come from the authenticated/session context wherever possible.

Do not trust an LLM-generated customer ID as the authorization mechanism.

For example:

```text
Authenticated session
        |
        v
customer_id = CUST-123
        |
        v
All tools enforce customer scope
```

A tool should reject:

```text
customer_id != authenticated_customer_id
```

where applicable.

# 21. Error Handling

The agent should gracefully handle:

### MongoDB unavailable

Tell the customer that the account information is temporarily unavailable rather than inventing a result.

### Tool failure

Do not claim success.

### Missing customer

Ask for identification or route to appropriate support.

### Ambiguous invoice

Ask a clarification question if multiple invoices could match.

### Conflicting financial data

Do not arbitrarily choose a value.

Surface the authoritative ledger/business rule or explain that the account requires review.

### Management decision unavailable

Say that the request is still under review.

Trigger when:

* Data is contradictory.
* Customer requests something outside agent authority.
* High-risk financial action is requested.
* Management review is required.
* Customer explicitly asks for a human.
* Agent cannot safely determine the answer.

# 26. Important Design Constraint

Do not build this as:

```text
LLM
 |
 └── MongoDB
```

Build:

```text
LLM / LangGraph
       |
       v
Controlled Tools
       |
       v
Business Services
       |
       v
Repositories
       |
       v
MongoDB
```

This separation is mandatory because the agent will eventually have write capabilities.

# 27. Future Multi-Agent Compatibility

The MVP must make it easy to add:

```text
Customer Rep Agent
       |
       +── Finance Agent
       +── Collections Agent
       +── Sales Agent
       +── Support Agent
       +── Credit Agent
       +── Approval Agent
       +── Delivery Agent
       +── Technical Agent
```

Do not implement those agents now.

Instead, implement:

```text
AgentRegistry
AgentGateway
AgentTask
AgentResult
```

and make delegation a first-class operation in the architecture.

The Customer Rep should remain responsible for the customer-facing conversation.

Specialized agents should return structured results.

# 28. Definition of Done

The MVP is complete when:

1. A customer can connect through WebSocket.
2. The session identifies the customer.
3. The agent maintains conversational state.
4. The agent can answer customer/account questions using MongoDB.
5. Sales, receipts, ledgers, vouchers and outstanding balances can be retrieved.
6. Against-reference and on-account receipts are treated differently.
7. The agent can search existing cases.
8. The agent can create a case.
9. The agent can update a case.
10. The agent can create an approval request.
11. The agent can retrieve management decisions.
12. The agent can communicate case/approval decisions.
13. The agent can analyze payment history through a controlled service.
14. The agent never invents financial or management information.
15. MongoDB is never exposed as an unrestricted LLM tool.
16. Customer-level authorization is enforced.
17. Tool calls are observable and traceable.
18. Errors are handled gracefully.
19. The architecture includes an Agent Gateway abstraction.
20. A future specialized agent can be added without redesigning the Customer Rep graph.

# 29. Implementation Approach

Before writing large amounts of code:

1. Inspect the existing repository.
2. Identify the current Python/runtime setup.
3. Identify the existing MongoDB schema/models.
4. Identify existing authentication/session infrastructure.
5. Identify existing WebSocket infrastructure.
6. Reuse existing abstractions where appropriate.
7. Do not invent MongoDB collection names or field names if they already exist.
8. Document assumptions where the existing schema is unclear.

Then implement the MVP incrementally:

```text
Phase 1
MongoDB + repositories
        ↓
Phase 2
Customer context + financial context
        ↓
Phase 3
LangGraph state + core graph
        ↓
Phase 4
Tools
        ↓
Phase 5
Cases + approvals
        ↓
Phase 6
WebSocket/session integration
        ↓
Phase 7
Agent Gateway abstraction
        ↓
Phase 8
Tests + observability + error handling
```

Do not prematurely implement a complex multi-agent system.

The goal is a **production-oriented single Customer Representative Agent whose architecture is already multi-agent ready**.
